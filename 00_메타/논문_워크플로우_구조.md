# 논문 워크플로우 구조 (순차 7단계 + 지속 트랙)

> 이 문서는 고정된 구조 정의입니다. 단계가 바뀌어도 이 파일은 수정하지 않고,
> 현재 진행 상태는 별도 파일 `진행상황.md`에서 관리합니다.
>
> **구조가 두 층으로 나뉩니다:**
> - **순차 단계(1~7)**: 앞 단계가 끝나야 다음으로 넘어가는 것들
> - **지속 트랙**: 특정 단계에 속하지 않고, 1단계부터 7단계까지 전체 기간 내내 병행하는 것들 (예전엔 "8단계"로 잘못 묶었던 부분)

## 순차 단계 (1~7)

| 단계 | 내용 | 도구 | 모델 | Effort | 서브에이전트 병렬화 |
|---|---|---|---|---|---|
| 1 | 연구주제 확정 | Projects 탭 Chat 모드 | Opus/Sonnet | High | ❌ 대화형, 병렬 불필요 |
| 2 | 자료조사 + 요약 | Cowork 또는 Claude Code | Haiku(검색) → Sonnet(요약) | Low → Medium | ✅ 하위갈래별 3~5개 |
| 3 | 교차검증 | Claude Code | Sonnet/Opus | Medium~High | ✅ 요약본별로 리뷰어 병렬 |
| 4 | 최종 취합 | Claude Code / Projects 탭 | Opus | High | ❌ 순차, 단일 |
| 5 | 가설·실험·검증 코드 | Claude Code | Sonnet(구현) / Opus(설계) | Medium~High | ✅ 독립적 실험별 병렬 |
| 6 | 논문 문서화 | Projects 탭 + Word(docx) | Opus/Sonnet | High | ⚠️ 챕터 초안만 부분 병렬 (통일성 패스 필수) |
| 7 | 방어논리/예상질문 | Projects 탭 Chat 모드 | Opus | High | ✅ 비판 관점별 병렬 |

## 지속 트랙 (1~7단계 내내 병행, 별도 "단계"가 아님)

| 트랙 | 하는 일 | 언제 손대는가 |
|---|---|---|
| 버전관리 | 로컬 폴더 GitHub push/pull, Google Drive에 원문·완성본 동기화 | 매 작업 세션 종료 시마다 커밋, PC 옮길 때마다 pull |
| 일정관리 (WBS) | 전체 일정 대비 진척률 갱신 | 매주 또는 각 순차단계 전환 시점마다 |
| 레퍼런스 관리 | BibTeX 등으로 참고문헌 정합성 유지 | 2단계에서 논문 추가될 때마다, 6단계 집필 중 계속 |
| 표절/유사도 점검 | 선행연구 문장 근접도 자가 점검 | 6단계 집필 중 문단 작성할 때마다 |
| 재현성 문서화 | 코드+데이터+환경(requirements.txt 등) 최신 상태 유지 | 5단계 실험 코드가 바뀔 때마다 |

## 단계별 상세

### 1단계 — 연구주제 확정
판단·좁히기의 반복이라 서브에이전트 불필요. 넘어갈 신호: 연구질문이 한두 문장으로 명확해짐 + 방법론 방향 대략 잡힘 + 선행연구 양이 적당함.

### 2단계 — 자료조사 + 요약/정리
검색(가볍고 빠름, 순차)과 요약(무겁고 느림, 병렬)의 역할 분리. 나누는 기준은 "주제"가 아니라 "하위갈래"(논문 주제는 하나, 그 안의 이론적/방법론적 갈래가 여러 개).

```
[1] 후보 논문 검색 (전체 주제 기준, 1회)
      ↓
[2] 하위갈래 3~5개로 분류
      ↓
[3] 하위갈래별 서브에이전트 병렬 실행
      Screener (Haiku, low effort) — 후보 스크리닝
            ↓
      Summarizer (Sonnet, medium effort) — 구조화된 요약
```

요약은 논문에 직접 인용될 수 있으니 Sonnet 밑으로 낮추지 않음. 비용은 "후보 거르기" 단계에서만 아낌.

### 3단계 — 교차검증
요약을 만든 에이전트가 자기 검증하면 편향되므로, 다른 서브에이전트가 원문·요약을 대조. 자료조사 자체 누락 검증(대표 논문 빠짐 없는지)은 Opus 추천.

### 4단계 — 최종 취합
순차 단일, Opus. 여러 갈래의 선행연구를 종합해 "내 연구가 기존 문헌 대비 어디에 위치하는지" 서술 — 워크플로우 전체에서 가장 판단력이 중요한 단계.

### 5단계 — 가설·실험·검증 (코드)
Claude Code 필수(실행·검증 루프가 핵심). 설계(novel한 부분)는 Opus·high effort, 구현·반복 실행은 Sonnet·medium effort. 독립적인 실험들(베이스라인 비교/하이퍼파라미터 분석/ablation study)은 병렬, 결과 해석은 순차 종합. 통계적 유의성 검정·재현성(seed 고정 등)은 명시적으로 지시.

### 6단계 — 논문 문서화
챕터별 초안은 서브에이전트로 병렬 작성 가능하나, 용어·문체 일관성을 위해 통일성 패스(단일 에이전트)는 반드시 순차로 후행.

### 7단계 — 방어논리/예상질문
심사위원 관점을 나눠서 병렬 "적대적 리뷰":
- 리뷰어1 (방법론 비판) — 왜 이 방법을 썼는가, 대안은 검토했는가
- 리뷰어2 (통계/타당성 비판) — 표본 수가 충분한가, 유의성 해석이 맞는가
- 리뷰어3 (novelty 비판) — 기존 연구 대비 진짜 새로운 게 뭔가

### 지속 트랙 상세

**버전관리**: 텍스트 산출물(요약/코드/초안)은 GitHub, 원문 PDF·완성 docx는 Google Drive로 역할 분담. 작업 세션 끝날 때마다 commit, 다른 PC에서 시작할 땐 반드시 pull 먼저.

**일정관리**: 7단계 구조 자체를 WBS 항목으로 놓고 진척률 추적. `진행상황.md`의 "다음 할 일"이 사실상 이 트랙의 실무 도구.

**레퍼런스 관리**: 2단계에서 논문이 추가될 때마다 Zotero/Mendeley 등에 등록, BibTeX로 내보내기 형식 유지.

**표절/유사도 점검**: 6단계 집필 중, 선행연구 문장을 얼마나 가깝게 따왔는지 문단 단위로 스스로 점검하도록 지시.

**재현성 문서화**: 5단계 실험 코드가 바뀔 때마다 `requirements.txt`, 데이터 버전, seed 값 등을 같이 갱신.

## 설계 원칙

- 판단력이 필요한 단계(1, 4, 6-통일성, 7) → 좋은 모델(Opus) + 높은 effort, 병렬화 안 함
- 물량은 많지만 독립적인 반복 작업(2-요약, 3-검증, 5-실험) → 서브에이전트 병렬화로 시간 단축
- 기계적/스크리닝성 작업(2-검색)만 → Haiku + low effort로 비용 절감
- 품질이 논문 신뢰도에 직결되는 부분(요약, 실험, 최종 글쓰기)은 절대 모델을 낮추지 않음
